2. 为什么选 React，不是 Vue

(参考时间: 03:01)

这个问题在开讲之前就已经在评论区被问过好几回了，这里一次说清楚。

2.1 同一类东西，只是写法不同

首先，React 和 Vue 是同一类东西：都是前端框架，要解决的问题一模一样，只不过写法不一样。就像上海话和粤语说同一件事，腔调不同而已。不存在"学了一个就放弃了另一个"——把其中一个的道理吃透，另一个也很快能触类旁通。

两个框架都非常优秀，没有高下之分。Vue 在国内用户很多，上手比较平缓，中文文档写得好。

2.2 用下载量说话

选 React 的主要理由是：它在全球范围内最流行，生态最大。

我们用另一个网站 npm trends 来对比——它统计 npm 上各个包的下载量。光看下载量这一项，React 就是 Vue 的好几倍。这说明有更多的项目是基于 React 做的，所以它的生态更大。

2.4 这门课的重点不是语法

对我们来说，选哪个真的没那么重要。这门课的核心也不是语法，而是先理解概念——只要理解了概念，我们就能够指挥 AI 把事给做了。

这两套框架用到的一些概念，比如说组件、状态、数据驱动界面，这一套逻辑是完全相通的。先挑一个把概念吃透，这才是听完这门课真正能带走的东西。

3. 框架是什么：一套规则

(参考时间: 06:06)

课程里反复提到"前端框架"，那框架到底是个什么？

graph LR
    A["框架 = 一套规则"] --> B["管某一摊事"]
    B --> C["前端框架<br/>管 UI 组件这一摊事"]
    B --> D["Web 框架<br/>（后端）管另一摊事"]

框架，其实就是管某一摊事的一套规则而已。

React 是一个前端框架，Vue 也是一个前端框架。这些前端框架管的是 UI 组件这一摊事。等到后面讲后端的时候，我们还会见到 Web 框架，那是管另一摊事的规则。

所以以后再看到软件开发里出现"框架"这个词，把它理解成一套规则就可以了。

4. React 的核心思想：界面即组件

(参考时间: 06:39)

React 定义的核心思想，是把用户界面定义成一个一个的组件。

这些组件把界面的数据、结构、样式、行为都包在组件里面，并且组件可以像搭积木一样组合或者嵌套。

📷 组件像搭积木一样组合与嵌套
在 B 站中打开 (00:07:04)

这和原来写 HTML 的方式就不一样了：

组织单元 分工方式
传统写法 页面 结构放 HTML，样式放 CSS，行为放 JS
React 思想 组件 数据、结构、样式、行为都收进组件

以前写 HTML 是基于页面来写的：把页面结构保存到 HTML，把样式保存到 CSS，把行为保存到 JS。而 React 的思想是基于组件来组织和管理项目，它的管理单元是组件。

自从有了框架，现在比较大一些的项目基本都是用框架来写的。

5. vanilla：不用框架的写法

(参考时间: 07:28)

但原来那种不用框架的写法也并没有过时。现在很多 vibe coding 的 slides 之类的基本都是不用框架的。

这种不用框架的写法一般被叫做 vanilla：不依赖任何第三方框架，只使用浏览器原生支持的 HTML、CSS 和 JavaScript 来建设功能的前端开发方式。我们今天这节课之前写的那些页面，都可以算 vanilla。

vanilla 这个词在英文里是"香草"的意思。为什么用这个词？因为买冰淇淋的时候，那种基础的、默认的口味一般就是香草味。所以软件行业借用了这个词，来表示原生的、没有添加额外框架或大规模扩展的版本。

这种叫法不只前端有：

  • 操作系统：vanilla Android、vanilla Linux；
  • 游戏：vanilla Minecraft。

大家了解一下就行，以后遇到这个词知道是什么意思就可以。但也别为这个词较真——网上见过有人吵架，说"只要用了第三方库就不能叫 vanilla"，这真的没必要争论。看到这个词，把它当成没有用框架的项目就可以了。

6. 浏览器只认三件套

(参考时间: 08:57)

关于框架，还有一个知识点必须强调：无论现在有多少前端框架，无论框架里定义了多少规则，浏览器是不管这些的。浏览器永远只认 HTML、CSS、JS 这三样。

这一点从来没有变过。React 也没有抛弃这三件套，它只是在这三件套上面加了一层更舒服的"作者层"。你按照 React 的方式去写，构建工具在背后把它编译回这三样，然后再喂给浏览器。

graph LR
    A["React 写法<br/>（作者层）"] -->|构建工具编译| B["HTML + CSS + JS"]
    B --> C["浏览器"]
    C --> D["页面呈现"]

所以 React 这种写法绝对离不开构建工具。没有构建工具那套翻译工序，浏览器根本不认 React 写出来的东西。

这也正是为什么这套课程设计时，先讲构建、再讲 React。

7. 把 React 装进项目

(参考时间: 09:55)

既然 React 是一套新规则，那我们就关注怎么把这套规则装进项目里。

具体操作层面其实平平无奇，就是会用 npm 去装几个包——还记得上一节课用到的 npm install 命令吗？跟我们装 anime.js 的方法是一样的，都是用 npm 装进来的。只不过 React 管的事更核心、更大。装上这几个包，我们的项目就拿到了 React 的那套规则，就能用它来写界面了。

另外还有一件事。刚才我们说 React 写出来的东西浏览器不认，得靠构建工具翻译回 HTML 三件套。那问题就来了：我们现在的构建工具用的是 Vite，Vite 凭什么就知道怎么翻译 React 呢？

所以 React 还会把"如何将自己翻译成基础前端"的这套规则告诉 Vite，Vite 只要照着这套规则去翻译就行。

7.1 "框架等于规则"的两层含义

(参考时间: 10:55)

到这里就清楚了，"框架等于规则"这句话其实有两层含义：

  1. 对开发者来说：它是一套更舒服的语法规则；
  2. 对构建工具来说：它还附带了一层规则——怎么把这种写法翻译回基础前端。

8.4 入口文件：组件负责"是什么"，入口负责"挂哪"

(参考时间: 20:09)

接下来怎么用呢？这个地方要注意。

ResultCard 这个文件它就是组件本身：它定义了这个卡片组件是什么、长什么样。但它自己不会自动跑到任何页面上去。那谁负责把它放到页面上呢？

我们还得新建一个文件，放在 src 下面（随便命名，这里叫它 result.jsx）。注意它没有放在 components 下面，而是直接放在 src 下面，跟 components 同级。

这个文件干什么事呢？它就是把这个 ResultCard 组件挂到 HTML 里面的某一个位置。这种负责把组件挂上页面的文件有一个名字，我们叫它入口文件——你可以理解为从 HTML 进入 React 的入口，也可以理解为从 React 进入我们项目的入口。

它的内容很简单，课件里有写法：

这几行不用完全读懂，直接说结论：它就是把这个 ResultCard 组件先 import 进来，然后去页面上找到一个名字叫做 result-root 的元素（或者说这么一个位置），把组件挂进去。

8.8 一句话总结组件

(参考时间: 26:26)

一个组件，就是把这些数据、结构、样式、行为这一整套收进同一个文件，然后封装成一个能够独立拎走的 UI 单元，再加上它自带的 import / export：要什么东西自己进口，然后把自己交出去。

这就好像是一个项目的一个零件。这就是 React 的地基——接下来我们整个项目都可以拿这种零件去打出来。

8.9 vanilla 与 React 共存只是学习态

(参考时间: 27:07)

一个零件看明白了。现在项目里同时有 vanilla 写法和 React 组件——但这只是我们作为学习来用的。

真正的项目开发中别这样：要么就是纯 vanilla，要么就是纯框架。因为这种"两掺"的状态其实提高了复杂度，可能导致一些小问题。

11.2 什么时候不该拆组件

(参考时间: 39:58)

另外这个页面里面还有什么呢？还有下面这俩 <article>。我们并没有把它们拆成组件，而是直接写在了这个 homepage 里头。

为什么不拆呢？因为它俩只在首页使用，内容也很简单。你拆出去呢，既换不来复用，又凭空多出两个文件，这样反而更碎。

所以拆组件就是为了能复用，以及为了让页面读着清爽。不要为了拆而拆。

graph TD
    A["一块东西要不要单独做成组件？"] --> B{"它会在多处用吗？"}
    B -->|是| Z["拆"]
    B -->|否| C{"拆出去能让页面更好读吗？"}
    C -->|是| Z
    C -->|否| D["不拆"]

要不要单独做成组件，你就问这样两句话：

  1. 它会在多处用吗？
  2. 拆出去能够让页面更好读吗？

如果这两条都不沾，那就没必要拆。

14. React 项目骨架全景

(参考时间: 46:27)

接下来好好看一看，一个 React 项目的骨架长什么样。它是一层一层套起来的：

graph TD
    A["index.html<br/>空壳，只提供挂载点"] --> B["main.jsx<br/>入口文件"]
    B --> C["App<br/>React 总管，决定显示哪个页面"]
    C --> D["HomePage"]
    C --> E["TextLabPage"]
    D --> F["Nav / PageHeading / article ..."]
    E --> G["Nav / PageHeading / InputCard<br/>ResultCard / AnimatedCardGrid"]
  • 最外面是 index.html，这是一个空壳，它只提供这样一个挂载点；
  • 这个挂载点依赖 main.jsx；
  • 然后这个 main.jsx 就把 App 给挂进来；
  • 这个 App 是React 的总管：它把不同的页面放进去（这里面的两个页面），并且决定着什么时候该显示哪一个页面；
  • 再往里面呢，就是这两个页面，以及这页面里面的这些零件。

我们这个项目就像是搭积木一样，就这样搭起来了。

现在我们整个项目中只剩下一个 HTML 文件了，并且它现在的作用只有一个：就是把 React 组件挂进来。那如果我们接下来再去做构建的时候，也就只会构建出来一个 HTML 文件了。这就是 React 框架的实现方式：只有一个 HTML 文件。

17. 生态：框架真正的护城河

(参考时间: 51:14)

课程的结尾，我们再思考一下"框架"这件事。

现在有这么多框架，而且框架本身就是一套让我们写得舒服的写法和规则，最后 Vite 再靠这一套规则来翻译框架写的东西。

如果我们想通这一层，你会不会冒出来一个念头：那如果我们自己有一套更好的代码组织的思路，我们是不是也能够创造一个新的框架呢？ 比如我定义我自己的写法，写完之后交给构建工具去跑——理论上是不是完全也可以？

没错，真的可以。造一个框架从技术上并不是什么遥不可及的事情。但是难的是什么呢？难的是这套框架有没有生态。

17.1 一个日期选择器的代价

(参考时间: 52:04)

假设你造了一个语法特别优雅的新框架。现在你要做一个后台管理系统，那么你需要一个日期选择器、一个数据表格，或者一些图表，或者是富文本编辑器这样的组件。

如果说你是用 React 或者是 Vue，这些东西早就有人做好了一行命令装进来，然后就能用——这两家的成套组件库都极其丰富。还记得这节课开头我说，选 React 或者是 Vue 主要是图它那个又大又厚的生态吗？这就是答案。

那如果是换成一个全新的框架呢？对不起，什么现成的都没有，全都得我们自己从零造。不说别的，就单单说一个日期选择器吧，看着简单，如果说你要真的把它做到好用、没有 bug、各种边界都对齐，那就能耗时好几天。

这就是生态。 一个框架值不值得用，很大程度上不是看它的语法有多么优雅、写起来有多简单，而是看它背后有多少现成的轮子能直接拿来用。

React 和 Vue 之所以是主流，最硬的护城河也就是它们背后那些海量的现成组件库、教程，还有替我们踩过坑的人。

所以为什么我们就在 React 和 Vue 里面挑，而不是去追求某一个更新潮的小众框架呢？因为生态决定了我们能不能站在别人的肩膀上。

还记得我们今天整理组件的时候用到的那个"复用"吧？我们复用的还只是我们自己写的两个组件而已。而框架的生态，让我们复用的是全世界别人写好的东西。

小结

(参考时间: 55:31)

本讲的内容就是以上这些。强烈建议大家跟着课程做一遍，并且每做一步都尝试一下这一步做的事情。

回过头看，这一讲其实只做了一件事：把上一讲的 vanilla 项目，一层一层地改造成 React 项目。而改造过程本身，就是理解 React 最好的方式——你会亲眼看到：

  1. 框架是一套规则，它有两层含义：给开发者的舒服写法，和给构建工具的翻译规则；
  2. React 的核心是组件：把一个 UI 单元的数据、结构、样式、行为收进同一个文件，用 import / export 对外交互；
  3. 组件负责"是什么"，入口文件负责"挂哪"——挂到 HTML 要入口文件，挂到组件内部不用；
  4. 一层一层往上拼：零件 → 容器组件 → Page 组件 → App → main.jsx → index.html，最后整个项目只剩一个 HTML 文件；
  5. 拆组件要问两个问题：会在多处用吗？拆出去更好读吗？都不是就别拆；
  6. 生态才是护城河：造框架不难，难的是有没有现成的轮子可以站在上面。
