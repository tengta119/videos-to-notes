5. 时间的陷阱：时区与 UTC 规范

(参考时间: 13:30)

在记录中引入时间字段看似简单，却暗藏着一个巨大的跨国工程陷阱——时区（Timezone）。

如果直接调用 datetime.now()，获取的是当前服务器所在操作系统的本地时间： * 若服务器部署在广州，记录显示 15:00； * 若服务器部署在美西硅谷，记录显示 23:00。 两台跨国服务器上的同样日志，物理时刻完全对不上，排查问题将陷入巨大混乱！

[!IMPORTANT] 全栈时间处理的黄金法则： 1. 存储时一律归一化为 UTC：UTC（协调世界时，伦敦格林尼治零度经线标准时）是全球通用的绝对物理时间刻度； 2. 展示时按用户当地时区渲染：例如中国用户按 UTC+8 转换为北京时间，旧金山用户按 UTC-7 转换。 内部系统通信与数据落盘永远只认 UTC ISO-8601 格式字符串（如 2026-09-15T02:40:00Z）。

步骤 2：封装底层文件读写函数

HISTORY_FILE = "history.json"

def load_history():
    """从磁盘文件中读取全部历史记录"""
    try:
        with open(HISTORY_FILE, "r", encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        return []

def save_record(record):
    """追加单条记录并全量持久化落盘"""
    records = load_history()
    records.append(record)
    with open(HISTORY_FILE, "w", encoding="utf-8") as f:
        json.dump(records, f, ensure_ascii=False, indent=2)

9. 方案反思：文件存储的三大致命天花板

(参考时间: 27:30)

至此，我们的简易文件存储系统运行良好。但在真实的互联网生产环境中，这种“基于单个文件的整存整取”模式隐藏着三个足以摧毁系统的致命隐患：

flowchart TD
    subgraph Bottleneck1 ["致命天花板 1：性能雪崩 (I/O 放大)"]
        AppendOne["新增 1 条数据"] --> LoadAll["必须在内存读出已有 10,000 条"]
        LoadAll --> DumpAll["必须将 10,001 条整份重写刷入磁盘"]
        DumpAll -->|O(N) 读写放大| IOHalt["磁盘 I/O 阻塞，响应延迟暴增"]
    end

    subgraph Bottleneck2 ["致命天花板 2：并发冲突 (脏写与脏读)"]
        UserA["用户 A: 分析'今晚夜色真美'"]
        UserB["用户 B: 分析'这车动力很足'"]
        UserA & UserB -->|同时读取| SameState["都读取到相同的前置 100 条"]
        UserA -->|第 1 毫秒写回 101 条| Overwrite1["写入文件 (含 A)"]
        UserB -->|第 2 毫秒写回 101 条| Overwrite2["覆写文件 (含 B 但抹杀 A!)"]

        Writing["正在写入 10MB 的 JSON 字符串..."]
        PowerCut["突然断电 / 进程崩溃 / 硬盘写满"]
        Writing --> PowerCut
        PowerCut --> CorruptJSON["末尾缺失花括号 }]"]
        CorruptJSON --> Panic["json.load() 语法报错，全部历史记录瞬间归零!"]

天花板 1：性能雪崩（I/O 读写放大）

观察 save_record 的逻辑：无论新记录多小，都必须将整个文件全量读入内存、再全量刷回磁盘。 当数据达到 10 万条时，哪怕只追加一个字，也必须承受整整 10 万条记录的磁盘 I/O 序列化与反序列化，系统吞吐量将出现断崖式下跌。

天花板 2：并发竞态（脏写与脏读）

📷 高并发下前后脚覆写导致一方数据凭空蒸发的脏写原理图解
在 B 站中打开 (00:29:45)

现代 Web 服务器是多线程/多进程并发处理请求的： 1. 用户 A（提交“今晚夜色真美”）与用户 B（提交“这车动力很足”）几乎在同一毫秒发起请求； 2. 两人同时执行 load_history()，内存中拿到的都是原本的旧数组； 3. A 在自身内存中追加后率先写回磁盘； 4. 紧接着 1 毫秒后，B 也将自己追加后的数组全量写回磁盘，强行覆盖了 A 刚写入的文件！ 5. 用户 A 的记录在没有任何报错的情况下凭空彻底蒸发！这就是计算机科学中臭名昭著的脏写（Dirty Write）。 同理，当一个请求写了一半，另一个请求刚好读取，读到的将是破损的中间状态，构成脏读（Dirty Read）。

天花板 3：一坏全坏（缺乏原子性 ACID）

在写回磁盘的纳秒窗口期内，一旦服务器突然断电或内存溢出崩溃，文件末尾可能只写了一半。 由于缺少关闭括号，下一次调用 json.load() 将直接抛出解析异常，导致整份文件的全部历史数据陪葬，不可恢复！

10. 业务合规深思与后续路线规划

(参考时间: 34:30)

在进入数据库实战前，我们还需要审视一个非技术层面的关键合规问题： 当前 history.json 把所有不相识访客的输入混在一起公开展出。

合理的业务边界是：每个用户只能查看自己曾经提交过的历史记录。 要做到这一点，系统必须具备识别用户的能力： 1. 第一层：会话体系（Session）：在不强制登录的前提下，利用 Cookie 机制记住当前浏览器，让同一个浏览器在多次请求与刷新间保持关联（我们将在第 29 讲 6.6 中深度攻坚）； 2. 第二层：账号与认证体系（Auth）：账号、密码、Token、加密与权限控制（涉及庞大的安全工程）。

在本讲中，我们完成了两项关键认知跃升与代码实践： * 实践落地：用最接地气的文件系统实现了持久化，掌握了时区与 UTC 处理的最佳实践，成功给文字实验室注入了“记忆”； * 瓶颈叩问：深刻论证了普通文件面对高并发在线增删查改时的无力感，为引入工业级存储扫清了认知障碍。
